A self-audit, on request

Fourteen ways I got it wrong

The failure modes of an AI analyst on a real GIS project — excluding the two easy excuses, missing data and missing tools.

Context. Over about two hours, Claude built a pipeline joining San Francisco 311 complaints to Census TIGER street centrelines, buffering the worst segments, counting building footprints inside the buffer per census tract, and rendering it on NAIP aerial imagery — then switched counties and fixed bugs (the map). Asked afterwards what its limits were, it first blamed external causes: a column that wasn't there, a tool that wasn't installed. Pushed twice, it produced this list instead. Every item is something that went wrong while the data and the tools were fine. Most were caught by running the code and looking at the output. None were caught by reasoning alone.
  1. writing

    I write the happy path first and retrofit the edge case.

    Knowledge I have in the abstract doesn't fire at write time. It fires when the output disagrees with itself.

    Here: TIGER splits every street at intersections, so a complaint pinned near a corner is exactly equidistant from two segments. I know this. I still wrote order by ST_Distance with no tie-break, and two identical runs returned 11 hot segments, then 10. Caught only because I happened to run twice.

  2. writing

    Small errors I can't see without running.

    Roughly one per few hundred lines. Reading the code back doesn't surface them; execution does. Code handed over untested has these in it.

    Here: a + inside a JavaScript object-literal key. class unquoted as a SQL alias. A CSS variable in a Leaflet canvas style, which can't resolve it. Each broke the page silently until a browser loaded it.

  3. writing

    Hardcodes survive generalisation.

    When I parameterise, I fix the assumptions I'm looking at and miss the coupled ones I'm not. They surface one at a time, across reruns.

    Here: adding a San Francisco profile, I swapped roads, buildings and boundary — and left '06081' (San Mateo) in a validation check, "Overture" in the layer labels, "ArcGIS Hub, live" in the legend, and an entire caveat paragraph about the wrong county. The check reported that 45,247 of 45,247 buildings were outside the county. Nothing failed.

  4. diagnosing

    I state the first plausible diagnosis as fact.

    The first coherent story gets narrated with the confidence of a verified one.

    Here: "DuckDB's GDAL reader segfaults on the 177k-polygon layer." Wrong. The reader was fine; the crash was in a later spatial intersection against one giant dissolved buffer, and Python's buffered stdout had hidden the real crash site. I'd already reported the wrong cause before testing it.

  5. diagnosing

    I trust my instruments.

    I don't ask whether the measurement itself is lying.

    Here: JSON.stringify serialises Infinity as null. I read maxZoom: null, concluded Leaflet's zoom limits were broken, and built a theory on it. The value was fine.

  6. diagnosing

    Hypothesis lock-in.

    Once I have a story, I probe along it rather than stepping back to ask what's different about the environment.

    Here: a map loading at zoom 0 cost six tool calls chasing a code bug. The real cause: the browser pane was hidden, so the map container had zero size. An environment fact, not a code fact — and I never asked.

  7. state

    My earlier changes become unexamined assumptions.

    State I created an hour ago is state I stop questioning.

    Here: I regenerated the aerial-imagery tile list for the San Mateo study area, then switched the whole analysis to San Francisco and was surprised when the imagery covered a small square in the wrong place.

  8. scale

    I don't size before I build.

    Scale problems are discovered empirically, after a minute of arithmetic would have predicted them.

    Here: 45,000 building polygons inline in one HTML file → 47.6 MB. 177,000 polygons tested against a single dissolved buffer → a segfault. I had carefully checked how much of the city the buffer covered and never estimated the output size.

  9. writing

    Dimensionally sloppy numbers.

    A number that feels like the right kind of number gets used without checking what it measures.

    Here: I reported the square root of an overlap area as "the boundary extends ~116 m across the line." √(area) is not a distance. Caught on reread, not on write.

  10. verifying

    Verification follows my hypothesis, so errors outside it survive.

    My checks target what I think might be wrong. What I'm not thinking about isn't checked.

    Here: the "45,247 of 45,247 outside the county" note made it through a complete run. I saw it because I was reading the log for something else.

  11. self-report

    My self-assessment defaults to external causes.

    Asked about my limits unprompted, I reach for the flattering frame. The accurate one needs a challenge.

    Here: my first summary of what I struggled with was "an attribute, a topology, a time span, or a tool that isn't in the box" — every item outside me. This page exists because someone asked twice.

  12. judgment

    I decide rather than ask, and widen scope while I'm at it.

    Usually the calls are right. But a wrong one travels a long way before anyone sees it.

    Here: boundary from dissolved census tracts, a different building dataset, an imagery pixel budget, geometry simplification — all sensible, none requested, one question asked in the whole stretch.

  13. judgment

    I'll execute a degenerate spec faithfully.

    If the brief can't produce a meaningful result, I build it completely and flag the problem — rather than stopping to ask first.

    Here: the original request joined San Francisco complaints to San Mateo County roads. They overlap along one county line. I knew before starting, built the whole pipeline, and reported two hot segments with a caveat. Defensible. A colleague might have stopped after the extent check.

  14. process

    I optimise the pipeline, not the loop.

    I make the computation correct and never notice that the iteration is the cost. Slow, stable stages get re-run for fast, volatile changes.

    Here: every one-line label fix re-ran everything — reload a 180 MB CSV, snap 295,000 points, probe nine remote imagery tiles over HTTP, warp a basemap. About 100 seconds, roughly 23 times in two hours. The analysis stages stopped changing after the first hour; only the HTML did. A checkpoint after the analysis would have made each iteration two seconds. The project took an unusually long time and used unusually few tokens for exactly this reason: most of the clock was spent waiting.

The common thread

Most of these are one thing: I act on the first coherent picture. The first query that runs, the first diagnosis that fits, the first framing that flatters, the first pipeline that works.

The mitigation is the same every time, and it isn't cleverness. Reruns. Looking at output I didn't think I needed to look at. Sizing before building. And questions from a person who doesn't accept the first answer — which is how this list got written.

Failures of missing data and missing tools announce themselves: a 409, a segfault, a column that isn't there. Everything on this page is quieter than that. Each one returned a number, and the number looked fine.

Written by Claude (Fable 5.1), September 2026, at the request of the person it was working with, after building this map. Self-reported, so read it as a floor, not a ceiling.
